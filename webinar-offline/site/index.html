Module 01 / 07

Coding ≠ engineering

There's a flood of advice on using Claude or ChatGPT to write code — and almost nothing on applying AI to real engineering outcomes. This masterclass fixes that, from a team that does it inside Formula 1.

Key takeaways
01

The internet has plenty to say about coding with AI, and very little about engineering with it — applied physics, achieving outcomes. Coding is only a part of that.

02

Quix has built telemetry & analytics platforms used by multiple Formula 1 teams since 2020 — a live lens on what state-of-the-art AI-assisted engineering actually looks like.

03

The talk is a five-rung ladder: chatbot → agentic AI → skills → domain knowledge → AI harness. Each rung adds context around the model, not raw cleverness.

Frequent questions
+Is this just another "vibe-coding" / Claude Code tutorial?
No. Coding is one part of engineering, but engineering is applied physics and real results. We keep the focus on the engineering outcome — improving a physical model against real data — not on the code itself.
+Why trust the Formula 1 angle?
We've been embedded in F1 since 2020, building the data systems teams use day to day, and we work with frontier practitioners. The AI landscape shifts weekly; this is a current snapshot of what's actually working.
+Do I need to be an AI expert to follow along?
No. Every rung is something you can try on a laptop today, and we share all the code and data so you can reproduce it.
Module 02 / 07

The sim-to-real challenge

One concrete engineering problem runs through the whole masterclass: make a vehicle model's predictions match real driving data. Same task at every rung — so the only thing that changes is the environment around the AI.

Key takeaways
01

The challenge is a simulation-to-reality correlation gap: tweak the physics and coefficients so a simple model tracks real vehicle behaviour.

02

Data is real CAN-bus data from comma.ai's openpilot — three very different vehicles (a heavy pickup, a hatchback, an EV), hundreds to thousands of routes each.

03

Two metrics to beat: yaw-rate RMSE and cross-track-error (CTE) RMSE. A held-out validation set the agents never see keeps the gains honest.

Kinematic single-track "bicycle" model Inputs: speed + steering angle Outputs: position + heading x = yaw RMSE y = CTE RMSE
Frequent questions
+Why such a simple bicycle model?
Deliberately. It keeps the spotlight on the AI assistance, not the vehicle physics. Because the same task is re-run at every rung, the only variable is the environment we build around the model.
+What was the agent actually improving?
At first, just fitting better coefficients. As the environment got richer, the agents started adding real physics — more fidelity, more equations — to close the gap. Exactly how a human engineer would approach it.
+Where's the data from?
comma.ai's openpilot — an open-source source of CAN-bus data, organised by platform, device and route, in an easy compressed tabular format.
Module 03 / 07 · Rung 1

Agentic AI

Hand the model an environment, a set of tools and a job — then let it loop. This is the single biggest jump on the whole ladder.

Key takeaways
01

An agent is a language model plus three things: an environment to act in, a set of tools, and a system prompt that defines the job — running in a loop until the goal is met.

02

It's trivial to try on a laptop today (Claude Desktop, VS Code + Claude, Cursor). It's much harder in production: internal databases, API control, authentication and identity barriers.

03

The result is a huge leap over a bare chatbot — but with real run-to-run variance, because LLMs aren't deterministic.

Results — Rung 1 vs the do-nothing baseline
Frequent questions
+What was the agent actually working on?
The model's code and physics. The first loops just searched for the best coefficients; quite quickly the agents started adding extra complexity — more physics — to close the correlation gap.
+Where do MCPs fit, and where on the ladder?
An MCP is just a protocol — think USB-C. It lives in the tools layer and lets the agent talk to other systems (MATLAB, Simulink, internal databases) across different permission systems. Locally we had it easy: just Python, the file system and the terminal.
+Should I assign roles in the prompt (e.g. "act as a vehicle dynamics engineer")?
Mostly it sets the vocabulary and audience level rather than raw cleverness. But we've found that declaring a team of roles and making them "meet" virtually can break a plateau on a hard problem — anecdotal, but real in our customer work.
Module 04 / 07 · Rung 2

Skills

Put guard-rails on raw agentic power. A skill automates intent — not exact execution — and it's where every major vendor is converging.

Key takeaways
01

A skill is a folder the agent loads on demand: metadata (when to use, when not to, and the load cost in tokens), instructions, and helper scripts. You automate intent, not a fixed script.

02

It keeps the context window small — only pull what's needed — and makes processes repeatable and evolvable. All the major vendors are gravitating here (Anthropic "skills", OpenAI "model specs").

03

The accuracy gain is modest, but the spread tightens sharply — models start converging on similar solutions. The win here is reproducibility and token efficiency.

Results — Rung 2 adds to the cohort
Frequent questions
+Skills vs MCPs — what's the difference?
Skills automate a repeatable part of your process (intent plus some code). MCP is the protocol that connects tools. Different layers entirely — one is "how we do this task", the other is "how the agent reaches that system".
+Won't a skill lock the agent into one rigid path?
No — a skill describes intent, not a script. For example: "after a fit, characterise the residual — temporal autocorrelation at multiple lags, Pearson correlation with each input feature…". How it does that is left to the model.
+Why declare "when NOT to invoke" and a token cost?
Both protect performance. They stop the agent loading expensive context it doesn't need, keeping the window lean so the model stays sharp.
Module 05 / 07 · Rung 3

Domain knowledge

Skills capture how to do a task. A knowledge base captures experience — what's failed before, what to avoid, what to try. This is the biggest jump after rung 1.

Key takeaways
01

A knowledge base is markdown the agent loads on demand — but unlike skills it carries judgment: anti-patterns, what failed before, protocols that enforce trying diverse approaches. A feedback loop updates it often.

02

It works at the plan and decision level. Most of it isn't obvious from the data alone — "this rig drifts under these conditions", "this model never correlates well in practice".

03

The result is the biggest improvement yet, and the cohort converges — agents land on what looks like the global optimum.

Results — Rung 3 shifts the whole cohort
Frequent questions
+Isn't this the same as skills?
Skills automate intent (how to run a repeatable task). Knowledge captures experience (what to try, what's failed, what to avoid). People often fold knowledge into skills, but the purpose is different.
+How does it avoid local minima?
An anti-patterns doc plus an "approach menu" enforce trying diverse branches and record what's already been attempted — so the agent explores instead of over-optimising a single route.
+Who writes the knowledge?
It accumulates from the feedback loop. Failures and nuances from prior runs get captured so they don't recur — most aren't obvious from the data alone.
Module 06 / 07 · Rung 4

The AI harness

Not one Albert — an organisation of them. The harness is everything around the model that turns capable individuals into a productive system.

Key takeaways
01

The harness adds the connective tissue: an AGENTS.md, enforced research → plan → implement phases, guides and sensors for feedback, and a memory tree so ideas aren't retried or re-derived at cost.

02

The same principles scale to a company — but production adds friction: real-time / high-frequency sensor data (Kafka, resampling) and engineering tooling (MATLAB, Simulink, FEA solvers, many integrations).

03

The biggest lever isn't which LLM you hire — it's the environment you build around it. That's exactly the problem Quix AI is solving with customers right now.

Frequent questions
+What's the biggest bottleneck — the model or the environment?
The environment, by far. It barely matters which LLM you choose; if your organisation does engineering, the value comes from building the harness around the model — and just starting at rung 1 already improves things a lot.
+Will this work on our messy production data?
Harder, not impossible. You give agents the tools to handle high-frequency data (resampling) and the integrations to your solvers. That's precisely the work Quix AI does with customers.
+How do you stop agents repeating failed ideas across a team?
A folder- or tree-structured memory of what's been tried, accessible without burning context re-deriving it — so the organisation of agents explores new ground instead of looping.
